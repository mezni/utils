## Summary

Initialize the BorneMap project with a complete monorepo structure including three frontend packages (ui-kit, domain-types, client-core), three backend microservices (auth-service, driver-service, admin-service), CI enforcement pipeline with 9 mandatory stages, three database schemas (platform_db with users/gis/inventory, analytics_db, keycloak_db), and SpecKit compliance enforcement layer. The enforcement kernel is fully specified for execution-grade validation.

**Constraints**:

- Hard-stop on any CI stage failure

**Scale/Scope**: Monorepo structure, 3 backend services, 3 frontend packages, 3 databases, 9 CI stages, ~114 initial tasks

## Enforcement Kernel Specification

### CI Execution DAG

**Stage Order** (strict linear sequence with artifact passing):

```
Stage 1: format_check
  ↓ Passes
  artifact: format_check_report.json

Stage 2: type_check
  ↓ Passes, consumes format_check_report.json
  artifact: type_check_report.json

Stage 3: dependency_graph_validation
  ↓ Passes, consumes type_check_report.json
  artifact: dependency_graph.json

Stage 4: identity_validation
  ↓ Passes, consumes dependency_graph.json
  artifact: identity_validation_report.json

Stage 5: schema_validation
  ↓ Passes, consumes identity_validation_report.json
  artifact: schema_validation_report.json

Stage 6: sqlx_compile_check
  ↓ Passes, consumes schema_validation_report.json
  artifact: sqlx_prepare_state.json

Stage 7: analytics_write_gate
  ↓ Passes, consumes sqlx_prepare_state.json
  artifact: analytics_gate_report.json

Stage 8: integration_tests
  ↓ Passes, consumes analytics_gate_report.json
  artifact: test_results.json

Stage 9: build_success
  ↓ Passes, consumes test_results.json
  artifact: build_state.json
```

**Failure Propagation Rules**:
- Hard-stop: Any stage failure immediately aborts all subsequent stages
- Deterministic exit codes: 0=success, 1=failure, 2=skipped
- No partial success allowed
- Each stage logs detailed failure reason to CI output

**Artifact Passing Model**:
- Each stage produces strict JSON artifact on success
- Next stage consumes previous artifact as input
- No side effects between stages
- All artifacts stored in `.specify/ci-artifacts/` for audit trail

### Enforcement Validator Specifications

#### 1. format_check

**Input**: All Rust source files in workspace

**Algorithm**:
- Run `cargo fmt --check --all`
- Parse output for failures

**Output**: JSON
```json
{
  "status": "passed"|"failed",
  "exit_code": 0,
  "summary": "X files formatted"
}
```

**Failure Signature**: Exit code 1 with file paths

---

#### 2. type_check

**Input**: cargo clippy output from format_check artifact

**Algorithm**:
- Run `cargo clippy --all-targets --all-features --workspace -- -D warnings`
- Parse for lint violations

**Output**: JSON
```json
{
  "status": "passed"|"failed",
  "exit_code": 0,
  "violation_count": 0,
  "summary": "0 clippy violations found"
}
```

**Failure Signature**: Exit code 1 with warning details

---

#### 3. dependency_graph_validation

**Input**: Cargo metadata from all workspace crates

**Algorithm**:
- Run `cargo tree --all`
- Parse workspace dependencies
- Detect forbidden patterns:
  - service → service imports
  - frontend → backend imports
  - shared-domain → services
  - ui-kit → client-core
- AST analysis for Rust crates (syn library)

**Output**: JSON
```json
{
  "status": "passed"|"failed",
  "exit_code": 0,
  "forbidden_edges": [],
  "summary": "No forbidden dependency edges found"
}
```

**Failure Signature**: Exit code 1 with edge list
```json
{
  "status": "failed",
  "exit_code": 1,
  "forbidden_edges": [
    {"source": "services/auth-service", "target": "services/driver-service"}
  ]
}
```

**AST Detection**: syn library parses Rust AST, looks for `use` statements that cross forbidden boundaries

---

#### 4. identity_validation

**Input**: All Rust source files from type_check artifact

**Algorithm**:
- Parse each file for entity identifiers
- Validate UUID usage in users table
- Validate nanoid(12) with PREFIX in entities (STA/CHG/OPR/EVT)
- Detect mixing violations

**Regex Patterns**:
- UUID: `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`
- STA-nanoid: `^STA[0-9a-zA-Z]{11}$`
- CHG-nanoid: `^CHG[0-9a-zA-Z]{11}$`
- OPR-nanoid: `^OPR[0-9a-zA-Z]{11}$`
- EVT-nanoid: `^EVT[0-9a-zA-Z]{11}$`

**Output**: JSON
```json
{
  "status": "passed"|"failed",
  "exit_code": 0,
  "violation_count": 0,
  "violations": []
}
```

**Failure Signature**: Exit code 1 with specific violations
```json
{
  "status": "failed",
  "exit_code": 1,
  "violations": [
    {
      "file": "services/auth-service/src/db/users.rs",
      "line": 15,
      "issue": "UUID found in entity identifier field"
    }
  ]
}
```

**Parser Boundary**: Detects which tables expect UUID vs nanoid based on table name in SQL migration files

---

#### 5. schema_validation

**Input**: All database migration files and schema definition documents

**Algorithm**:
- Parse all `.up.sql` files for table definitions
- Validate required tables exist per database
- Check indexes and constraints match data-model.md
- Validate schema ownership per constitution

**Output**: JSON
```json
{
  "status": "passed"|"failed",
  "exit_code": 0,
  "missing_tables": [],
  "summary": "All schemas validated"
}
```

**Failure Signature**: Exit code 1 with missing tables

---

#### 6. sqlx_compile_check

**Input**: Cargo metadata and migration files from schema_validation artifact

**Algorithm**:
- Set `SQLX_OFFLINE=true` environment variable
- Run `cargo sqlx prepare --all -- --database-url postgres://user:pass@localhost:5432/dbname`
- Check if `.sqlx/` directory exists with metadata
- Run `cargo sqlx prepare --check --all`
- Verify all queries compile-time verified

**Output**: JSON
```json
{
  "status": "passed"|"failed",
  "exit_code": 0,
  "queries_verified": 0,
  "summary": "All SQL queries compile-time verified"
}
```

**Failure Signature**: Exit code 1 with unverified queries

**Caching Strategy**:
- SQLx metadata cached in `.sqlx/` directory
- CI caches `.sqlx/` directory to avoid regeneration
- Regeneration triggered only when migrations change

---

#### 7. analytics_write_gate

**Input**: All Rust source files and migration files from sqlx_compile_check artifact

**Algorithm**:
- Grep for write SQL patterns: `INSERT`, `UPDATE`, `DELETE`, `CREATE TABLE`
- Parse migration files for service ownership markers
- Validate only driver-service has write access to analytics_db
- Check that admin-service and auth-service do NOT have write access

**Output**: JSON
```json
{
  "status": "passed"|"failed",
  "exit_code": 0,
  "write_operations": [],
  "summary": "Only driver-service has analytics write access"
}
```

**Failure Signature**: Exit code 1 with violations
```json
{
  "status": "failed",
  "exit_code": 1,
  "violations": [
    {
      "file": "services/admin-service/migrations/0001_init_inventory.up.sql",
      "operation": "CREATE TABLE",
      "service": "admin-service",
      "service_allowed_to_write": false
    }
  ]
}
```

**Verification**:
- Static analysis: grep for write operations
- Migration analysis: parse `.up.sql` files
- Service ownership check: compare service name to database ownership

---

#### 8. integration_tests

**Input**: Test results from all cargo test runs

**Algorithm**:
- Run `cargo test --workspace --all-features`
- Parse test output for failures
- Count passed/failed tests

**Output**: JSON
```json
{
  "status": "passed"|"failed",
  "exit_code": 0,
  "test_count": 100,
  "passed": 100,
  "failed": 0,
  "summary": "100 tests passed"
}
```

**Failure Signature**: Exit code 1 with failed tests

---

#### 9. build_success

**Input**: Build state from test results artifact

**Algorithm**:
- Run `cargo build --release --workspace`
- Verify all crates compile successfully
- Check for any warnings

**Output**: JSON
```json
{
  "status": "passed"|"failed",
  "exit_code": 0,
  "binaries_built": 6,
  "summary": "All workspace crates built successfully"
}
```

**Failure Signature**: Exit code 1 with build errors

### Database Ownership Enforcement (Runtime)

**PostgreSQL Roles**:

```sql
-- Platform DB
CREATE ROLE bornemap_admin;
CREATE ROLE bornemap_driver;
CREATE ROLE bornemap_auth;

-- Analytics DB
CREATE ROLE bornemap_analytics_writer;
CREATE ROLE bornemap_analytics_reader;

-- Permissions
GRANT ALL PRIVILEGES ON DATABASE platform_db TO bornemap_admin;
GRANT CONNECT ON DATABASE platform_db TO bornemap_driver;
GRANT CONNECT ON DATABASE platform_db TO bornemap_auth;

GRANT ALL PRIVILEGES ON DATABASE analytics_db TO bornemap_analytics_writer;
GRANT CONNECT ON DATABASE analytics_db TO bornemap_analytics_reader;
```

**Schema-Level Ownership**:

```sql
-- platform_db
CREATE SCHEMA auth; GRANT USAGE ON SCHEMA auth TO bornemap_admin;
CREATE SCHEMA gis; GRANT USAGE ON SCHEMA gis TO bornemap_driver;
CREATE SCHEMA inventory; GRANT USAGE ON SCHEMA inventory TO bornemap_admin;

-- analytics_db
CREATE SCHEMA telemetry; GRANT ALL ON SCHEMA telemetry TO bornemap_analytics_writer;
GRANT USAGE ON SCHEMA telemetry TO bornemap_analytics_reader;
```

**Migration Isolation**:

- Each service has isolated migration files
- Migrations forward-only only (no rollback)
- No destructive operations
- CI validates migration scripts before execution

### Gate 1: Service Topology Lock (PASS)

**Constitution Requirement**: Exactly three services MUST exist, each on a fixed port: auth-service (3000), driver-service (3001), admin-service (3002). No additional services.

**Compliance Status**: ✅ PASS

**Justification**: The plan creates exactly three services as mandated. No additional services or topology changes are planned in Sprint 0. This is the foundational setup that establishes the required topology.

**Verification**: Directory structure creates `services/auth-service`, `services/driver-service`, `services/admin-service`. Configuration files will specify ports 3000, 3001, 3002.

---

### Gate 2: Identity Dual System (PASS)

**Constitution Requirement**: Two independent identity systems: Keycloak UUID (human) and Platform nanoid(12) with PREFIX (business). No mixing allowed.

**Compliance Status**: ✅ PASS

**Justification**: The plan includes database schemas for platform_db (users table with UUID, gis, inventory tables with nanoid(12) PREFIX) and creates infrastructure for Keycloak. The identity validation tools (01_validate_identity.sh) will enforce this separation.

**Verification**: Schema definitions will use UUID for users, PREFIX-nanoid(12) for STA/CHG/OPR/EVT entities. Validation scripts will check identity format.

---

### Gate 3: Data Ownership (PASS)

**Constitution Requirement**: Every data domain has exactly one owning service. Cross-service writes forbidden.

**Compliance Status**: ✅ PASS

**Justification**: The plan defines database ownership: platform_db users (auth-service), gis (driver-service), inventory (admin-service), analytics_db (driver-service with admin read-only). This establishes the single-writer rule.

**Verification**: Database schemas will have proper ownership. CI analytics gate validation tool (03_validate_analytics_gate.sh) will enforce write permissions. Migrations will be isolated by service.

---

### Gate 4: Contract-First (PASS)

**Constitution Requirement**: Contract definition → Backend implementation → Frontend implementation in that order. No other sequence.

**Compliance Status**: ✅ PASS

**Justification**: The plan creates `apps/packages/domain-types` as a contracts-only package. Service skeletons will use this as dependency. Sprint 0 sets up the foundation; actual contracts will be defined in later sprints, following the proper order.

**Verification**: Domain-types package will be a contracts-only Rust package with DTOs and event schemas. Services will depend on it. No runtime logic in domain-types.

---

### Gate 5: SQLx Compile-Time (PASS)

**Constitution Requirement**: All SQL queries MUST be compile-time verified via SQLx. CI MUST run `cargo sqlx prepare --check`.

**Compliance Status**: ✅ PASS

**Justification**: The plan includes SQLx offline verification (S0-020) and a validation tool (05_sqlx_policy_check.sh) to enforce this. All SQL queries will use compile-time verified SQLx types.

**Verification**: CI pipeline includes sqlx_compile_check stage. Validation script checks for raw SQL strings. Cargo.toml will configure SQLx for offline verification.

---

### Gate 6: CI Enforcement (PASS)

**Constitution Requirement**: 9-stage CI pipeline with hard-stop on any failure.

**Compliance Status**: ✅ PASS

**Justification**: The plan creates a complete CI pipeline with all 9 stages: format_check, type_check, dependency_graph_validation, identity_validation, schema_validation, sqlx_compile_check, analytics_write_gate, integration_tests, build_success. Each stage has hard-stop enforcement.

**Verification**: `.github/workflows/ci.yml` will implement all 9 stages. Tools/ci_guard.sh will provide enforcement. 06_ci_guard_final.sh will be the final gate.

---

### Gate 7: Forbidden Edges (PASS)

**Constitution Requirement**: No service→service imports, no frontend→backend imports, no shared-domain→services, no ui-kit→client-core, no circular dependencies.

**Compliance Status**: ✅ PASS

**Justification**: The plan establishes proper dependency chains: services → shared-domain → shared-infra, ui-kit → domain-types → client-core. No forbidden edges exist in the planned structure.

**Verification**: Directory structure enforces separation. Dependency validation tool (02_validate_deps.sh) will check for forbidden edges. CI will include dependency_graph_validation stage.

### Enforcement Kernel Complexity

The enforcement kernel introduces complexity to ensure constitutional compliance:

| Complexity Component | Why Needed | Simpler Alternative Rejected Because |
|---------------------|------------|-------------------------------------|
| 9-stage CI pipeline with artifact passing | Constitution mandates strict sequential enforcement | Single-stage CI would allow violations to pass through unchecked |
| AST-based dependency validation (syn library) | Detect forbidden cross-service imports | Static analysis would be brittle and miss complex cases |
| SQLx compile-time verification with offline mode | Constitution requires no dynamic SQL construction | Runtime SQL would violate contract-first and SQLx compile-time requirements |
| PostgreSQL role-based permissions | Constitution requires single-writer enforcement | Database-level constraints cannot be enforced at CI level |

All complexity is justified by constitutional requirements and is necessary for true enforcement-grade compliance.
