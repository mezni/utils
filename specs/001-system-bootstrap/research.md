# Research: System Bootstrap & Enforcement Kernel

**Feature**: 001-system-bootstrap
**Date**: 2026-06-21

## Unknowns Resolved

### 1. Monorepo Package Architecture

**Decision**: Use workspaces for Rust monorepo management

**Rationale**:
- Cargo workspaces provide built-in multi-crate dependency management
- Centralized Cargo.toml for workspace configuration
- Easy parallel building and testing of all crates
- Standard Rust ecosystem approach

**Alternatives Considered**:
- Submodules: Rejected — Git submodules are not well-suited for Rust monorepos; Cargo workspaces are the idiomatic solution
- Flat directory with manual dependency management: Rejected — No version pinning, difficult dependency resolution, manual integration
- Yarn workspaces (Node.js): Not applicable — This is a Rust project

**Implementation Notes**:
- Create root Cargo.toml with `[workspace]` section
- Each package in apps/packages and services will have its own Cargo.toml
- Workspaces allow cross-package testing and development
- Shared dependencies in `[workspace.dependencies]` section

### 2. CI Pipeline Stage Details

**Decision**: Implement each of the 9 CI stages with specific tooling

**Rationale**:
- Format check: cargo fmt (standard Rust formatting)
- Type check: cargo clippy for stricter type checking
- Dependency graph validation: cargo tree with cycle detection
- Identity validation: custom shell script checking UUID/nanoid usage
- Schema validation: SQLx schema validation + database schema verification
- SQLx compile check: cargo sqlx prepare --check
- Analytics write gate: grep for write operations, static analysis
- Integration tests: cargo test with all test suites
- Build success: cargo build

**Alternatives Considered**:
- Using pre-commit hooks instead of CI: Rejected — CI is the single source of truth; pre-commit can miss violations
- Only running tests as CI stages: Rejected — Constitution mandates strict gate enforcement before tests
- Custom tooling for all stages: Rejected — Standard tools (cargo fmt, cargo clippy, cargo test) are battle-tested

**Implementation Notes**:
- All stages use hard-stop: `set -e` in bash scripts
- Error messages must be clear and actionable
- Each stage outputs pass/fail status to CI logs
- 06_ci_guard_final.sh runs all validations and enforces the final gate

### 3. Database Schema Design

**Decision**: Use PostgreSQL with SQLx for schema management and migrations

**Rationale**:
- PostgreSQL is widely supported and reliable
- SQLx provides compile-time verification of queries
- Migrations can be versioned and managed separately
- Supports JSONB for flexible telemetry/analytics data
- Excellent support for indexes, constraints, and performance tuning

**Alternatives Considered**:
- SQLite: Rejected — Not suitable for production workloads and concurrent access
- MySQL: Rejected — Less strict type system than PostgreSQL
- Manual schema management (no migrations): Rejected — Version control and rollback support critical

**Implementation Notes**:
- Use SQLx migrations in `migrations/` directory
- Each service has its own migration files (forward-only)
- platform_db has 3 schemas (users, gis, inventory)
- analytics_db has 3 schemas (telemetry_events, analytics_events, system_events)
- Keycloak DB is auto-generated by Keycloak installation

### 4. Service Skeleton Structure

**Decision**: Use actix-web for web framework with cargo projects

**Rationale**:
- Actix-web is high-performance and well-suited for Rust async services
- Explicit, idiomatic Rust with strong type system
- Easy health endpoint implementation
- Native support for PostgreSQL via sqlx
- Async/await pattern simplifies concurrency

**Alternatives Considered**:
- Tokio runtime with raw HTTP: Rejected — Too much boilerplate, error-prone
- Axum: Rejected — Actix-web is more established in production use
- Rocket: Rejected — Less strict async handling, ecosystem smaller

**Implementation Notes**:
- Each service is a separate cargo binary in `services/<name>/`
- Cargo.toml for each service defines dependencies (sqlx, actix-web, serde)
- main.rs implements health endpoint and HTTP server
- Configuration via TOML files (not hardcoded)
- Separate ports: 3000, 3001, 3002 per constitution

### 5. Identity Validation Pattern

**Decision**: Use regex patterns to validate UUID vs nanoid formats

**Rationale**:
- Shell script validation is lightweight and fast
- Regex patterns can enforce exact formats
- Easy to integrate into CI pipeline
- Can detect violations early

**Alternatives Considered**:
- Rust runtime validation in CI: Rejected — Shell is faster for quick validation
- Custom validation tools: Rejected — Over-engineering for simple format checks
- Database-level validation: Rejected — CI must validate before code reaches database

**Implementation Notes**:
- UUID pattern: `[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}`
- nanoid(12) with PREFIX pattern: `^STA[0-9a-zA-Z]{11}|^CHG[0-9a-zA-Z]{11}|^OPR[0-9a-zA-Z]{11}|^EVT[0-9a-zA-Z]{11}$`
- Validate all Rust code using grep, clippy, and static analysis
- Fails CI if mixed usage detected

### 6. Analytics Write Gate Enforcement

**Decision**: Use grep for write operations + static analysis + CI gate

**Rationale**:
- Driver-service must be the only writer to analytics_db
- CI gate must fail if admin-service or auth-service attempts writes
- Simple and effective for MVP
- Can be enhanced later with database-level permissions

**Alternatives Considered**:
- Database-level permissions: Rejected — CI gate is the first line of defense; database checks are too late
- Runtime middleware: Rejected — Runtime enforcement cannot prevent code from being committed
- Linting rules: Rejected — Linting is advisory; CI gate is mandatory

**Implementation Notes**:
- 03_validate_analytics_gate.sh checks for write SQL patterns
- Monitors database connection initialization and migration files
- CI stage runs before database creation to catch violations early
- Uses grep for common write patterns (INSERT, UPDATE, DELETE, CREATE TABLE)

### 7. SpecKit Extensions Configuration

**Decision**: Implement before/after hooks for plan and tasks commands

**Rationale**:
- SpecKit provides structured workflow enforcement
- Hooks ensure consistency and compliance
- Can automate common tasks (formatting, validation)

**Alternatives Considered**:
- Manual compliance checks: Rejected — Too error-prone; automation ensures consistency
- No hooks: Rejected — SpecKit enforcement layer would not be effective

**Implementation Notes**:
- Configure git extension for auto-commit hooks
- Define before/after hooks for plan, tasks, clarify commands
- Hooks check for proper markers and structure
- All hooks are optional by default to avoid developer friction

### 8. Docker Compose for Local Development

**Decision**: Provide optional docker-compose.yml for local service orchestration

**Rationale**:
- Easier local development with database and service orchestration
- Consistent environment across developer machines
- Optional so it doesn't add complexity for those who prefer manual setup

**Alternatives Considered**:
- Manual service start: Rejected — Error-prone, inconsistent setup
- Kubernetes: Rejected — Too complex for local development, overkill
- No orchestration: Rejected — Harder to get started, more manual setup

**Implementation Notes**:
- docker-compose.yml defines 3 services (auth, driver, admin) + PostgreSQL + Redis
- Services connect to PostgreSQL on named volumes
- Persistent volumes for database data
- No network exposure to public (localhost only)
- Easy to start with `docker-compose up`

### 9. Keycloak Realm Export

**Decision**: Create realm export file for future use

**Rationale**:
- Enables consistent realm configuration across environments
- Allows quick setup of Keycloak in staging/production
- Tracks required realm configuration (clients, roles, etc.)

**Alternatives Considered**:
- Manual realm setup: Rejected — Time-consuming and error-prone
- Programmatic setup: Rejected — Requires Keycloak client library, too complex for MVP
- No realm configuration: Rejected — Essential for identity management

**Implementation Notes**:
- Export current realm to JSON file
- Include realm name, roles, clients, and mappings
- Place in infrastructure/ for easy access
- Document in infrastructure README
- Can be imported to other Keycloak instances

## Research Summary

This research phase has resolved all technical unknowns and established the architecture for the System Bootstrap feature. The decisions prioritize:

1. **Standards Compliance**: Using Cargo workspaces, actix-web, and PostgreSQL for production-quality foundations
2. **CI Enforcement**: 9-stage pipeline with hard-stop enforcement for architectural integrity
3. **Developer Experience**: Optional Docker Compose for easy local development
4. **Future-Proofing**: Infrastructure ready for Keycloak and Redis integration

All implementations follow the constitution constraints and SpecKit standards. The next phase will define data models and contracts for the services.
